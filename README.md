# Churn risk dashboard

Finds the telecom customers most likely to leave, explains why with SHAP, and suggests a
retention action matched to each customer's drivers and contract. It's built on the tuned XGBoost
model from my MSc Business Analytics dissertation (University of Greenwich), served with FastAPI
and a plain HTML/CSS/JS front end with no build step.

> **Proof of concept.** Built on IBM's *Telco Customer Churn* sample dataset, a fictional
> California telco with 7,043 customers. Every figure is computed on the 1,409 held-out test customers,
> who were not used for training or calibration.

| Headline (test set) | Value |
|---|---|
| ROC AUC | **0.855** |
| Churners reached by contacting the riskiest 20% | **51%** (191 of 374; 2.6× lift) |
| Revenue at risk, next 12 months | **$334k** (376.5 expected churners) |
| Estimated net saving from a retention campaign* | **$38.7k** |
| Calibration error (ECE), raw → calibrated | **13.9% → 1.9%** |

\*Illustrative assumptions, editable in the app: contact the riskiest 20%, 25% of contacted
would-be churners stay, $15 per contact, $60 incentive per customer kept, 12 months of revenue kept.

## What's in it

- **Overview:** four headline numbers, editable campaign assumptions (the saving updates live), and
  three real example customers (high, medium and low risk) that load with one click. Each shows the
  calibrated probability, SHAP drivers, a suggested action and a live "what if?" re-score.
- **Segments:** risk by contract, tenure band, internet service, protection add-ons, tech support or
  payment method, filterable by contract, internet, tenure and risk band. Predicted risk is plotted
  against the actual churn rate, with expected churners and monthly revenue at risk per segment.
- **Customers:** highest risk first. Each customer shows its top risk drivers, and opens to the full
  SHAP breakdown, a retention action and the assistant.
- **Model:** ROC curve, cumulative gains/lift, a before-and-after calibration diagram with Brier, log
  loss and ECE, a duplicate audit, limitations, and a "How it was built" panel.

### Calibration

The model was trained with `scale_pos_weight = 2.77`, which inflates raw probabilities: it predicted
an average of 40.5% churn against an actual rate of 26.5%. Platt scaling is fitted on **5-fold
out-of-fold predictions from the training partition** and never touches the test set. It is then applied
to the saved model, so every score, sum and dollar figure in the app is calibrated.

| Test set | Raw | Platt (used) | Isotonic (comparison) |
|---|---|---|---|
| Brier score | 0.160 | **0.133** | 0.134 |
| Log loss | 0.472 | **0.405** | 0.429 |
| ECE | 0.139 | **0.019** | 0.019 |
| Mean predicted (actual 0.265) | 0.405 | **0.267** | 0.268 |

Platt scaling is linear in log-odds, so SHAP values scaled by the Platt slope stay exactly additive on the
calibrated scale. Calibration is monotone, so ranking and AUC are unchanged.

### Retention actions

Rules in `app/actions.py` turn each customer's risk-raising SHAP drivers into up to three steps. For
example: month-to-month contract → offer a 12-month contract; one-year contract → early renewal
to two-year; electronic check → switch to auto-pay; fibre → service-quality check; no tech support →
trial. The channel depends on the risk band: a call within 7 days for High risk, email/SMS for Medium,
no contact for Low. Customers on a two-year contract get service-quality steps rather than contract
offers. Demographic drivers (gender, age, partner, dependants) are shown but never turned into actions.

### Duplicate check

- 0 duplicate customer IDs, 0 exact duplicate rows.
- **73 rows (33 groups) share identical model inputs.** 18 of those groups contain both a churner and a
  stayer; 12 groups straddle the train/test split (13 test rows).
- All 73 are 1-month, month-to-month customers, whose total charges equal one monthly bill, and every group spans
  different cities, so they are different people with the same simple profile. **They are kept**, and the test AUC
  without the overlapping rows is 0.8549 (vs 0.8546), so they do not inflate the headline.

```
 data/IBM_Telco_...csv ─┐                          browser: static/index.html + app.js + styles.css
 source_model/          │                              │  fetch JSON (same origin, CSP 'self')
   best_xgb.joblib ─────┤                              ▼
                        ▼                          FastAPI  app/main.py
 scripts/build_artifacts.py                          ├─ security headers, body-size cap, generic errors
   ├─ same features as dissertation (asserted)       ├─ strict pydantic schemas   app/schemas.py
   ├─ reproduce 80/20 split, check AUC 0.8546        ├─ /api/summary  /api/segments  /api/customers
   ├─ 5-fold OOF on train → Platt calibration        ├─ /api/score (what-if)      /api/model
   ├─ duplicate audit, ROC, gains, reliability       └─ /api/assistant ──► app/assistant.py
   └─ export booster to XGBoost JSON                        │  off unless HF_TOKEN; per-IP + daily
        │                                                   │  limits; template fallback
        ▼                                                   ▼
 artifacts/  model.json  calibration.json  ──────►  app/model.py (fixed paths only)
             portfolio.json  model_report.json        xgboost Booster → margin → Platt → probability
                                                      pred_contribs (TreeSHAP) × Platt slope → drivers
                                                      app/actions.py → retention action
```

The runtime never unpickles anything. The model is loaded from XGBoost's native JSON format, from a
fixed path.

## Run it locally

Python 3.13:

```bash
cd churn-dashboard
python3.13 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
uvicorn app.main:app --port 7860
# open http://127.0.0.1:7860
```

Or with Docker:

```bash
docker build -t churn-dashboard .
docker run --rm -p 7860:7860 churn-dashboard
# optional assistant: docker run --rm -p 7860:7860 -e HF_TOKEN=... churn-dashboard
```

The assistant is **off unless `HF_TOKEN` is set** (a Hugging Face token with "Make calls to Inference
Providers" permission, added as a Space secret). Optional settings: `LLM_MODEL` (default
`openai/gpt-oss-120b`), `ASSISTANT_PER_IP_PER_MINUTE` (4), `ASSISTANT_PER_IP_PER_DAY` (20) and
`ASSISTANT_GLOBAL_PER_DAY` (300).

Tests and checks:

```bash
pip install -r requirements-dev.txt
pytest -q                                   # 63 API tests, incl. malformed and hostile input
python scripts/screenshots.py http://127.0.0.1:7860 docs/screenshots   # uses installed Chrome
pip-audit -r requirements.txt
```

Rebuild the artefacts (only needed if the model or data changes). Put the CSV in `data/` first; see
`data/README.md`.

```bash
python3.13 -m venv .venv-build && .venv-build/bin/pip install -r requirements-build.txt
.venv-build/bin/python scripts/build_artifacts.py
```

## Deploying as a Hugging Face Space

The front matter at the top of this file configures a Docker Space on port 7860. The image uses
`python:3.13-slim` and `xgboost-cpu`, and runs as uid 1000. The CSP allows iframe embedding only from
`huggingface.co` and `*.hf.space`. `.gitattributes` routes model and binary formats through Git LFS; no
file currently exceeds HF's 10 MB limit (the largest, `artifacts/portfolio.json`, is about 0.7 MB).
Notebooks, `.env` files, caches and the raw CSV are git-ignored, and `.dockerignore` allowlists only
`app/`, `static/`, `artifacts/` and `requirements.txt`.

## Security

- `/docs`, `/redoc` and `/openapi.json` are disabled (404).
- Strict pydantic validation: `extra="forbid"` everywhere, `strict=True` on JSON bodies (no `"3"` → 3
  or `"yes"` → true), enum-only categorical fields, bounded numbers, cross-field consistency checks,
  a regex for customer IDs, and a 280-character cap on questions.
- Errors return a short generic JSON body with field names only. Submitted input, stack traces and
  upstream errors are never echoed. Request bodies over 4 KB are rejected.
- The front end never uses `innerHTML`: all text, including LLM output, goes in via `textContent`.
  CSP is `script-src 'self'` with no inline scripts or styles.
- No CORS middleware, so cross-origin requests are not allowed at all (nothing wildcard).
- Model files are read only from fixed paths in `app/config.py`, in JSON format (no pickle at runtime).
- Assistant: off without `HF_TOKEN`; per-IP (rightmost public `X-Forwarded-For` hop) and global daily
  limits; answer length cap; template fallback on any failure. The token is read from the environment
  only when calling the model. It is never logged, never returned, and failures are logged by exception type only.

## Limitations

- **Fictional sample data** from one quarter of an invented California telco, with no later period to
  test on (no out-of-time validation).
- **No behavioural data:** no complaints, usage, network quality, satisfaction or contract end dates.
  The model says *who* is at risk, not *what went wrong*.
- **Prediction is not persuasion.** The model ranks who will leave, not who an offer would change. The saving
  rests on an assumed save rate; a controlled test or uplift model is needed to measure it.
- **Revenue, not profit:** there is no margin data. The campaign maths assumes a churner's bill is lost for the whole period.
- **SHAP shows association, not cause.** Correlated inputs share credit. Demographic inputs are model features;
  fairness has not been audited.
- **Calibration is approximate:** it is fitted on out-of-fold models with the same settings, then applied to the final model.
- **Demo infrastructure:** single process, in-memory rate limits that reset on restart, no auth, no monitoring.
- Customers in the dataset include people who already left that quarter, so "revenue at risk" shows
  the method rather than forecasting a real book.

## What I'd do next

Validate on a later period; add complaint, usage and network data; run a controlled retention test to
measure the real save rate and move to uplift modelling; monitor drift and calibration; review the
demographic features for fairness.
